# 第一步计划：原始数据理解与质量核验

## 目的与起点

从原始数据重新开始，判断 `winequality-red.csv` 和 `winequality-white.csv` 每行、每列实际代表什么，原始数据是否能可靠地进入后续探索分析。当前分支 `codex/wine-quality-project` 从 `main` 的原始数据提交开始；另一个 worktree 的分析试验不作为本步输入、结论或验收证据。

字段说明 `data/winequality.names` 称每行是一份葡萄酒样本，11 个理化指标为输入，`quality` 是至少 3 位专家评分的中位数。红酒和白酒分文件保存，均使用分号分隔。文件没有样本 ID、采集时间、品牌、年份或价格，因此相同数值的行是否为同一样本尚不能判断。

## 输入与保全

只读输入：`data/winequality-red.csv`、`data/winequality-white.csv`、`data/winequality.names`。执行开始和结束时记录每个文件的路径、字节数、SHA256；不得覆盖、清洗或另存为“新原始数据”。本步所有结论仅针对这两份 CSV 中的行，不推广到全部葡萄酒。

## 具体工作

1. **核对记录格式和字段。** 分别读取两份 CSV，核对表头、分隔符、行宽、行数、字段类型和所有值能否解析；将 `winequality.names` 的字段含义与实际表头逐列对应。保留文件原有红酒/白酒分类，不把两表直接拼接为一类样本。
2. **核对数据质量。** 分红酒和白酒统计空值、无法解析的数值、非有限值、`quality` 非整数或超出 0–10 的值、完全相同的整行及各字段取值范围。重复行只标记和计数，不据此删除，因为缺少样本 ID。
3. **建立后续分析起点。** 分红酒和白酒列出 `quality` 的每个分值的行数及占本类全部行的比例，并检查频数合计等于各自原始行数。此处只描述分布；不分析指标相关性、不训练模型，也不宣称红白酒差异的因果原因。
4. **独立复核。** 用与主统计代码不同的读取/统计路径，从原始 CSV 重算文件 SHA256、行数、表头、`quality` 频数、空值、无效值和重复行数；逐项对照输出和报告。

## 产物与用途

所有新文件置于 `steps/01_data_understanding/`：

- `outputs/data_profile.json`：逐文件保存输入指纹、表结构、质量检查和 `quality` 分布，供下一步探索分析使用。
- `src/profile.py`：复现主统计的代码；`checks/verify.py` 与 `checks/verification.json`：独立复核代码及逐项结果。
- `execution.jsonl`：记录输入版本、运行命令、环境、参数及成功或失败的尝试。
- `report.md`：解释原始记录、主要数据变化（本步应为零）、质量问题及其对下一步的影响，并就近链接实际产物。

执行者可在不改变本计划范围的前提下确定代码实现细节。新产物不得复制另一个 worktree 的试验结果作为本步结果。

## 验收与停止条件

- 两份 CSV 均能完整读取；表头与字段说明的 11 个理化指标加 `quality` 对应。若存在不一致，报告逐列列出，不把不一致隐藏为通过。
- 每项行数、分值频数及比例的分母明确；各分值频数之和等于本文件原始行数。输出和报告数字一致。
- 独立复核逐项重算并对照；不能仅以主程序运行成功代替复核。若发现异常或检查失败，保留原始证据、标记本步未通过，先解释原因，不进入下一步。
- 执行前后原始文件字节数与 SHA256 一致；本步不删除、不填补、不修改任何原始行。
- 主 agent 从实际输出、代码和原始 CSV 验收技术正确性，再单独判断解释是否有证据、后续业务用途是否成立；用户确认理解后才制定下一步计划。

本计划获用户同意且执行 agent 确定后才开始业务执行。
